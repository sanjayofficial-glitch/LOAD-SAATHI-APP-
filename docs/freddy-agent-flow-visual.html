TL;DR. Freddy today is a fully tested but inert edge endpoint. It is never triggered by timers, cron, or a model. It fires only when all four ingredients line up: ① a POST with Authorization: Bearer <Clerk template JWT> · ② body carries filters · ③ FREDDY_ENABLED=true in the server env · ④ auth + marketplace secrets configured. Missing any one → a sanitized exit at that exact gate. With the flag off (current reality), every request stops at node 3 with a disabled banner — and by design, no auth code ever runs, which is why the verification must happen in staging (§ below).

6 Behind-the-logic footnotes — the why behind each design line

Kill switch runs before auth. One env var, FREDDY_ENABLED=false, makes the whole endpoint a no-op without touching a DB, a secret, or a model. Consequence (found in review): a flag-off deploy can't test authentication — that's why Stage B exists. Treating a wrong env value as "off" means misconfiguration is safe, never that the endpoint vanishes silently.
The caller's JWT is the DB credential. Freddy never holds a superuser key. It verified you, so it queries as you; row visibility stays exactly what you'd get on the normal Loads page. Postgres RLS is the boundary — the agent adds zero privilege.
The tool never builds queries freely. Only 4 filters map to fixed PostgREST fragments; status list, ordering, limit and columns are compiled constants. Text inputs are bounded (1–80 chars, NUL-rejected) and LIKE-wildcards escaped so even % or _ can't widen a search.
Everything is sanitized. DB failures become Marketplace search failed (HTTP 503). No bodies, tokens, secrets or SQLSTATE ever reach a client; config errors log only a variable name. A bad token and an expired token return the identical 401 — nothing to fingerprint.
Timing & volume caps. One read/query, 50 rows max, 8 s timeout, 10 req/min/IP, 16 KiB body, 2000-char message. A misbehaving client is cheap to contain; in-memory limiter per instance is a known Phase-3 upgrade point.
Why “no filters” returns tool:null instead of searching. With no model there is no intent detection — running an unfiltered marketplace query on every “hello” would spend reads guessing. The stable {tool:null} keeps behavior honest & cheap until the LLM phase replaces the guess.
